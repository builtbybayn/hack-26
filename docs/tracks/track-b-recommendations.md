# Track B: Paper recommendations

Read [the track overview](README.md) first for the rules every track follows.

## Goal

Given the paper being read, recommend **real** papers to read alongside it:

- **Background:** papers that teach the paper's foundational concepts (what to read first).
- **Related:** papers on the same question or method.

Every recommendation must come from a scholarly database and link to a real record. A language
model may explain _why_ a paper is relevant, but must never produce the paper itself: no invented
titles, authors, DOIs, or links. This is the white paper's hardest rule for this feature.

## Step 1 (first hour): contract

`src/types/research.ts` (proposal; adjust in your first PR):

```ts
import type { ApiResponse, CommonErrorCode } from "./api";
import type { ParsedDocument } from "./ingestion";
import type { DocumentAnalysis, IntelligenceErrorCode } from "./intelligence";

/** A paper as returned by a scholarly database. Never generated by a model. */
export interface PaperRecord {
  /** Provider-scoped id, e.g. "openalex:W2741809807". */
  id: string;
  title: string;
  authors: string[];
  year?: number;
  venue?: string;
  doi?: string;
  abstract?: string;
  url: string; // landing page that resolves
  openAccessPdfUrl?: string;
  citationCount?: number;
  provider: "openalex" | "semantic-scholar";
}

export interface PaperRecommendation {
  paper: PaperRecord;
  kind: "background" | "related";
  /** Concept ids from the analysis this paper addresses. */
  conceptIds: string[];
  /** One or two sentences, grounded in the record's title/abstract. Null if not generated. */
  reason: string | null;
}

export interface RecommendationsRequest {
  document: ParsedDocument;
  analysis: DocumentAnalysis;
  limit?: number; // default 8, max 20
}

export interface RecommendationsResult {
  recommendations: PaperRecommendation[];
  /** Exactly what was searched, so results are reproducible and explainable. */
  queries: {
    text: string;
    kind: "background" | "related";
    provider: string;
    resultCount: number;
  }[];
  warnings: string[]; // e.g. "Abstract unavailable for 3 results."
}

export type ResearchErrorCode = "SEARCH_PROVIDER_ERROR" | "SEARCH_RATE_LIMITED";
export type RecommendationsResponse = ApiResponse<
  RecommendationsResult,
  ResearchErrorCode | IntelligenceErrorCode | CommonErrorCode
>;
```

Add `MOCK_RECOMMENDATIONS` in `src/lib/api/research-mock.ts`. Use real papers in the mock (copy
real records from the provider), so the UI is designed against realistic data.

No results is not an error: return an empty list and a warning.

## Step 2: provider adapter

```ts
// src/lib/research/provider.ts
export interface ResearchProvider {
  name: PaperRecord["provider"];
  search(query: string, options: { limit: number; signal?: AbortSignal }): Promise<PaperRecord[]>;
}
```

Start with **one** provider and make it solid:

- **OpenAlex** (recommended first): broad coverage, works search, abstracts, open-access links.
  Note: abstracts come back as an inverted index and need to be rebuilt into text.
- **Semantic Scholar**: good relevance and a recommendations endpoint; rate limited without a key.

Check each provider's current authentication and rate-limit rules before building. Put any key in
`.env.local` and read it server-side only. Handle rate limits (HTTP 429) as
`SEARCH_RATE_LIMITED`, with a timeout on every request (`timeoutSignal` in
`src/lib/api/route-helpers.ts` shows the pattern).

Unit-test the adapter by mocking `fetch` with a recorded real response saved under
`tests/fixtures/`. Tests must not hit the network.

## Step 3: building queries and ranking

The analysis already contains what you need:

- `analysis.understanding.subject` and `topics` → **related** queries.
- `analysis.graph.foundationalConceptIds` → concepts with no prerequisites in the graph, the
  basics this paper assumes → **background** queries (for example, "introduction to <concept>",
  or the concept name plus "tutorial" or "review").
- `document.title` and `metadata` → exclude the paper itself from results (match DOI or title).

Rank with plain code first (term overlap with the paper's topics, recency, citation count,
open-access availability), deduplicate by DOI, then by normalized title. Then optionally call
`generateText` from `src/lib/ai/gemini.ts` (created by Track A) to write each `reason` from that
record's title and abstract only. If Gemini fails or isn't configured, return `reason: null`
rather than failing the request.

## Step 4: route and UI

- `POST /api/recommendations`, body `RecommendationsRequest`, zod-validated (reuse
  `documentInputSchema` from `src/lib/intelligence/schema.ts`). Use `success` / `failure` /
  `routeError` from `src/lib/api/route-helpers.ts`.
- `src/features/recommendations/RecommendationsPanel.tsx`: "Read first" and "Related" groups.
  Each card shows title, authors, year, venue, the reason, and a link. Show "abstract not
  available" honestly when it's missing. Build against the mock first, then mount it with one
  line in `DocumentIntelligence.tsx`.
- **Saving papers (later):** if you add saved papers, add a `papers` store to
  `src/lib/browser-store.ts`. Announce it first, because it bumps `DB_VERSION`.
